# Phase 2B-3: Controlled Terraform Process Boundary

**Status:** Implemented (`com.iacagent.iacagent.runner`, `com.iacagent.iacagent.runner.jdbc`). The first phase in this trust boundary that launches a real OS process - but only three non-mutating Terraform commands, behind a closed, allowlisted, internally-constructed argv, with an empty-by-default environment. No `terraform init`/`validate`/`plan`/`apply`, infrastructure mutation, or state mutation is representable through this trust boundary's own closed operation model.

**Precise claim (twice-amended - see §13):** an earlier revision of this phase's own acceptance report stated "zero capability for init/validate/plan/apply... anywhere in this codebase," which review correctly identified as broader than the evidence supported - a pre-existing, unrelated, unrestricted execution surface (`com.iacagent.iacagent.CommandRunner`, reachable via a live Spring endpoint) was found during this phase's own manual inspection. The first amendment made it unreachable from the running application by removing the endpoint; review correctly identified that as necessary but insufficient, since "unreachable" is a dependency-graph property, not a capability boundary - the generic `String... command` + `ProcessBuilder` surface still existed in `src/main` and could be wired up again by any future production code with nothing stopping it. The final amendment removed that capability outright: `TerraformCliAdapter`/`TerraformExecutionService` (and the `PipelineRequest`/`PipelineResult` records that existed only to serve them) were deleted from `src/main`, and `CommandRunner` was moved to `src/test` (still directly unit-tested by `Phase1bTests`, but never compiled into the running application). The property actually proven, precisely: **no `RunnerOperation`/`ControlledTerraformOperation` value, argv shape, or code path within `com.iacagent.iacagent.runner` can represent `init`/`validate`/`plan`/`apply` or any infrastructure/state mutation, and `com.iacagent.iacagent.runner.ControlledTerraformProcess` is the sole process-spawning class anywhere in `src/main` - no generic, non-allowlisted execution capability exists in production source at all, structurally verified by `ProductionExecutionSurfaceTests`.**

**Upstream binding references:** `docs/phase-2b2-runner-hardening.md` (this phase's identity/ledger/workspace trust boundary is preserved unchanged, not replaced), `docs/phase-2b1-controlled-runner.md`, `docs/roadmap-phase-2.md`, `docs/phase-2a-execution-contract.md`, `docs/phase-2a-threat-model.md`, `docs/Master-Prompt.txt`.

**What this phase answers, and what it deliberately does not:**

```text
Answers:
  Can the runner launch a real process at all?    -> yes, exactly one class does this: ControlledTerraformProcess
  What can it run?                                -> terraform version -json / fmt -check / show -json only
  What environment does the process see?          -> empty-by-default, allowlisted entries only, never System.getenv()
  What happens on a timeout, or runaway output?    -> the process (and descendants, best-effort) are terminated; bounded evidence is recorded
  Is the plan re-verified right before launch?     -> yes - a final TOCTOU hash recheck, independent of ControlledRunner's own earlier check

Does NOT answer:
  provider/plugin initialization or execution      -> not attempted; see SS4
  backend initialization or remote state access    -> not attempted; see SS4
  terraform plan (a new plan)                      -> not attempted; see SS4
  terraform apply / any infrastructure mutation    -> not attempted, and structurally impossible - no such operation, argv shape, or code path exists
```

## 1. Executable Trust Model

`TerraformExecutableProvider.resolve() -> TerraformExecutableResolution` is the only source anything in this package consults for the Terraform binary. `HostConfiguredTerraformExecutableProvider` is the reference implementation, built with the exact same discipline `HostAttestedRunnerIdentityProvider` established in Phase 2B-2 for identity - kept as an **independent implementation, not a shared refactor**, so that already-accepted class is left completely untouched by this phase:

- `trustedToolRoot` is resolved to its real path once, at construction, by trusted bootstrap code.
- Each `untrustedRoot` (expected to include at least the runner's workspace root and any repository-checkout root) is similarly resolved once at construction, with the same nearest-existing-ancestor real-path fallback Phase 2B-2 uses for a root that doesn't exist yet.
- `executablePath` must, at construction, resolve under `trustedToolRoot` - checked eagerly.
- On **every** `resolve()` call (no caching): the leaf path is rejected outright if it is a symlink; the path is then resolved to its **current** real path and must fall under the trusted root and outside every untrusted root (this is what catches ancestor-directory symlink substitution introduced after construction); the resolved file must be a regular, executable file.

Path-safety alone (`TerraformExecutableResolutionOutcome.RESOLVED`) proves only "safe to read and execute something at this location" - it does **not** prove this is the trusted Terraform binary. That is a separate, second check.

## 2. Executable Integrity (Hash) and Version Verification (amended)

`ControlledTerraformOperationCoordinator.verifyExecutable()` runs before every single operation attempt: resolve (per §1), then recompute SHA-256 over the resolved file's actual bytes and compare against `TerraformExecutableDescriptor.expectedSha256()`. A mismatch blocks (`TERRAFORM_EXECUTABLE_HASH_MISMATCH`) before any process is ever launched - re-verified on every attempt, not cached, so a binary swapped in after an earlier successful check is caught on the very next one (`Phase2b3Tests#binaryReplacedAfterInitialValidationBlocksOnPerLaunchRecheck`).

**Original design, rejected on review:** version verification was a separate, second kind of check that only `TERRAFORM_VERSION` performed - `TERRAFORM_FMT_CHECK`/`TERRAFORM_SHOW_PLAN_JSON` relied on the SHA-256 match alone, reasoning that a hash match to a known release is at least as strong a version proof as a self-reported string. Review correctly rejected this: `TerraformExecutableDescriptor.expectedVersion()` exists specifically so a hash-trusted binary reporting an unexpected version still blocks, and the accepted contract never made that check optional for two of the three operations.

**Current design:** every operation now requires a `VerifiedTerraformExecutable` attestation (`realPath`, `observedSha256`, `observedVersion`, `verifiedAt`) before it may launch its own command. `ControlledTerraformOperationCoordinator.obtainVerifiedExecutable` establishes one - by actually running `terraform version -json` and comparing the result against `expectedVersion` - whenever no still-valid cached attestation exists for the **current** hash of the **current** executable; a cached attestation is reused only when a freshly-recomputed hash still matches the one it was verified against, so a binary swap immediately invalidates it. `executeVersion` always runs its own real check (never served from cache, since reporting a genuine, fresh version reading is that operation's whole purpose) and refreshes the shared cache as a side effect of success, so a subsequent `FMT_CHECK`/`SHOW_PLAN_JSON` call against the same still-unchanged binary does not need to launch a redundant version-check process (`Phase2b3Tests#versionAttestationIsReusedAcrossCallsForAnUnchangedBinaryButNotAcrossAReplacedOne` proves the reuse via an invocation counter). The SHA-256 recheck inside `obtainVerifiedExecutable` still runs fresh on every single call, immediately before whichever command actually launches - the attestation only ever shortcuts the version-checking *process*, never the hash recheck. A binary whose hash is trusted but whose reported version is wrong blocks `FMT_CHECK`/`SHOW_PLAN_JSON` before their own command ever runs, proven with a marker file the fixture would create only if it had (`Phase2b3Tests#wrongReportedVersionBlocksFmtCheckBeforeItEverRuns`, `#wrongReportedVersionBlocksShowPlanJsonBeforeItEverRuns`); their evidence now carries the bound `terraformVersionObserved` on success rather than `null` (`#fmtCheckEvidenceCarriesTheObservedVersionOnSuccess`, `#showPlanJsonEvidenceCarriesTheObservedVersionOnSuccess`).

## 3. Closed Command Builder

`TerraformCommandFactory` is the only place a `ControlledTerraformCommand` is constructed. Every argv element originates from a fixed program constant (`"version"`, `"-json"`, `"fmt"`, `"-check"`, `"-no-color"`, `"-recursive"`, `"show"`), the trusted executable's own resolved real path, or an internally-derived workspace/artifact `Path` - never a `RunnerRequest` field, repository content, PR text, LLM output, or an environment variable. There is no method anywhere in this package shaped like `execute(String)`, `execute(String...)`, `runCommand(...)`, or `shell(...)` (`Phase2b3Tests#controlledTerraformProcessExecuteAcceptsOnlyAFullyTypedCommand`, `#terraformCommandFactoryHasNoMethodAcceptingArbitraryArgumentLists`). No shell quoting logic exists anywhere, because no shell is ever invoked.

Exact argv shapes:
```text
terraform version -json
terraform fmt -check -no-color -recursive <trusted-workspace>
terraform show -json <internally-staged-plan-path>
```

## 4. Why INIT / VALIDATE / PLAN (and APPLY) Are Deliberately Excluded

`terraform init` crosses a new trust boundary this phase does not attempt to model: it may access module/provider registries, download provider/module binaries, initialize a backend, and later execute provider plugin binaries it just downloaded - none of which this phase's executable-trust model (a single, pre-verified, pinned binary) has any story for. `terraform validate` generally depends on an already-initialized working directory and provider schemas, so it inherits the same gap. `terraform plan` may additionally require provider execution, backend/remote-state access, and cloud credentials - none of which exist anywhere in this phase. `terraform apply` is out of scope for all of Phase 2B, independent of any of the above, since it is the actual mutation boundary. All four remain **structurally** impossible in this phase, not merely policy-excluded: `ControlledTerraformOperation` has no value for any of them, so no argv exists that could represent one, and the source scan (§13) additionally confirms the literal command text is absent everywhere in the package.

## 5. Closed Operation Enum: Two Layers

`RunnerOperation` gained three values (`TERRAFORM_VERSION`, `TERRAFORM_FMT_CHECK`, `TERRAFORM_SHOW_PLAN_JSON`) - the outer, public request contract, dispatched by `ControlledRunner`. `ControlledTerraformOperation` is a **separate**, smaller, internal enum with the same three values, used by `TerraformCommandFactory`/`ControlledTerraformProcess`/`TerraformProcessEvidence` - deliberately independent of `RunnerRequest`/`ControlledRunner`/the approval/ledger machinery, so the process-boundary subsystem is usable and testable entirely on its own. `ControlledRunner` is the only production caller that ever constructs a `ControlledTerraformOperation`, mapping its own `RunnerOperation` value across.

## 6. Bounded Process Environment

`TerraformProcessEnvironmentPolicy` (a **new, sibling** implementation of `ProcessEnvironmentPolicy` - `AllowlistProcessEnvironmentPolicy` from Phase 2B-2 is untouched) builds a map starting from nothing and adds exactly five entries: `TF_IN_AUTOMATION=true`, `TF_INPUT=0`, `CHECKPOINT_DISABLE=1` (suppresses Terraform's own upgrade-check network call - the allowed operations need no network at all, see §11), `HOME=<workspace>/home`, `TMPDIR=<workspace>/tmp`. Never reads `System.getenv()`.

`ControlledTerraformProcess.execute()` enforces the critical rule at the actual launch point:
```java
builder.environment().clear();
builder.environment().putAll(command.environment().variables());
```
`ProcessBuilder`'s own environment map starts pre-populated with the current process's environment; clearing it first is what makes "empty by default" actually true rather than aspirational. `Phase2b3Tests#environmentIsClearedBeforeLaunchAndHostAmbientVariablesDoNotPropagate` proves this behaviorally: the host JVM's own real `PATH` (necessarily non-empty on any dev/CI machine) never appears in the child, and `AWS_ACCESS_KEY_ID`/`GITHUB_TOKEN` never propagate. (One portability caveat recorded honestly: some `/bin/sh` implementations set their own POSIX-mandated default `PATH` internally when they observe none in their environment at all - that is shell-internal behavior, not evidence of host-PATH leakage, so the test asserts "the host's real PATH value never appears," not "the child's shell reports a literally empty PATH.")

## 7. Executable/PATH Ownership

No caller-controlled executable or `PATH` value exists anywhere in this phase. The executable path is fixed entirely by trusted bootstrap code (§1); `PATH` is never one of the five variables `TerraformProcessEnvironmentPolicy` adds, so no process launched by this phase ever has a `PATH` at all, and `Phase2b3Tests#pathEnvironmentVariableDoesNotSelectTheBinary` proves a decoy binary sitting somewhere a hypothetical PATH lookup would find it is never chosen.

## 8. Working Directory

The Terraform working directory is always the request's own `RunnerWorkspaceManager`-created workspace - the same one Phase 2B-1/2B-2 already isolates per request (hash-derived naming, real-path containment checks, no path influence from request fields). `RunnerWorkspaceManager.revalidate(Path)` (new, additive) re-verifies the workspace's real path still falls under the configured root immediately before a Terraform launch, rather than relying solely on the check performed when the workspace was first created possibly seconds earlier in the same request's pipeline - used by `TERRAFORM_FMT_CHECK`'s coordinator path.

## 9. STDIN

`ControlledTerraformProcess.execute()` closes the process's stdin (`process.getOutputStream().close()`) immediately after starting it - the child observes EOF, never an inherited terminal or parent input stream, so nothing can prompt for interactive input. `Phase2b3Tests#stdinIsClosedRatherThanInherited` proves this with a fixture that reports whether it received EOF or actual data.

## 10. STDOUT / STDERR Bounds

Each stream is read on its own daemon thread into a bounded buffer (`ControlledTerraformProcess.BoundedStreamReader`); defaults are 10 MiB (stdout) / 2 MiB (stderr), both constructor-configurable. The moment either bound would be exceeded, that reader stops accumulating and the polling loop in `execute()` observes the overflow flag and terminates the process (§12) rather than continuing to await it. `stdoutSize`/`stderrSize` reflect only what was actually read before the bound was hit - the true (uncaptured) total size past that point is never claimed to be known. Truncated output is never treated as valid: `Phase2b3Tests#outputLimitExceededNeverBecomesSucceededEvenIfExitCodeWouldHaveBeenZero` proves a script that would otherwise exit 0 still yields `OUTPUT_LIMIT_EXCEEDED`, never `SUCCEEDED`.

## 11. Timeout and Process-Tree Termination

Every command carries a finite, runner-configured (never request-configured) `Duration timeout`. `execute()` polls (every 20ms) for process exit, output-bound overflow, or timeout elapsed - whichever comes first. On timeout or output-limit overflow, `destroyProcessTree(Process)` runs: `ProcessHandle.descendants()` are asked to `destroy()` first, then the process itself, with a brief grace period before escalating to `destroyForcibly()` on both if still alive. `Phase2b3Tests#timeoutTerminatesTheProcessDeterministically` proves the timeout path; `#descendantProcessIsBestEffortTerminatedOnTimeout` proves a background-forked child stops advancing after the parent is killed (best-effort and inherently timing-sensitive - documented as such, with the test itself abstaining rather than failing if the child fixture never got far enough to prove anything either way, consistent with the phase's own allowance to document this limitation rather than force a flaky guarantee).

## 12. Network Assumptions

None of the three allowed commands require network access - `version -json` and `fmt -check` are purely local, and `show -json` operates only on an already-staged local plan file. `CHECKPOINT_DISABLE=1` (§6) removes the one incidental network call Terraform itself might otherwise attempt. No network isolation is implemented at the OS/container level in this phase - that remains a production runner-sandbox concern (Gate D, §16).

## 13. Source Scan and Exclusive Execution Authority (amended)

`Phase2b3Tests#processBuilderAppearsOnlyInControlledTerraformProcess` (superseding the now-narrower `Phase2b1Tests#runnerPackageContainsNoProcessInvocationOutsideTheControlledTerraformProcessClass` and `Phase2b2Tests#runnerPackageStillContainsNoProcessOrShellInvocationAfterPhase2b2`) enforces: `ProcessBuilder` appears in exactly one file (`ControlledTerraformProcess.java`) **within `com.iacagent.iacagent.runner`**; `Runtime.exec`/`Runtime.getRuntime().exec`, `/bin/sh`, `"bash"`, `bash -c`, `cmd.exe`, `powershell`, and every `terraform init/validate/plan/apply/destroy/import/state/force-unlock/taint/untaint/refresh/workspace` literal are absent everywhere in that package, with no exception.

**A real, reachable bypass was found during this phase's own manual inspection of `src/main` beyond the `runner` package - and closed, not merely disclosed.** `com.iacagent.iacagent.CommandRunner` (Phase 1C-era; `ProcessBuilder` with an arbitrary `String... command`, guarded only by a denylist substring-matching a handful of destructive Terraform subcommands - notably NOT catching a plain `terraform apply` without `-auto-approve`) was, via `TerraformCliAdapter` → `TerraformExecutionService`, wired to a live Spring REST endpoint: `IacAgentController`'s `/pipeline` and `/execute-pipeline` mappings accepted a caller-supplied `workingDirectory` and ran a real `init → providers schema → fmt → validate → lint → security → test → plan → show` sequence against it with no allowlist, no executable trust model, and no environment isolation whatsoever - a parallel, unrestricted execution authority sitting alongside everything this phase (and Phase 2B generally) built to prevent exactly that. (`IacAgentService.executePlan`, behind `/apply`/`/execute`, was checked too and is pure simulation - a list of textual step descriptions, no process-spawning capability at all - so it required no change.)

**First-round remediation (Option A: made unreachable from production, Phase 1 machinery preserved as-is):** `IacAgentController`'s `terraformExecutionService` field and its `/pipeline`/`/execute-pipeline` mapping were removed entirely - no code path in the running Spring application constructed or invoked `TerraformExecutionService` (or, transitively, `TerraformCliAdapter`/`CommandRunner`) anymore. `LegacyExecutionSurfaceTests` (new, top-level `com.iacagent.iacagent` package) is the structural proof: it scans every class in that package for a Spring stereotype marker (`@RestController`/`@Controller`/`@Service`/`@Component`/`@Configuration`/`@Bean`/`@SpringBootApplication`) and asserts none of them references `CommandRunner`/`TerraformCliAdapter`/`TerraformExecutionService` (comments stripped first, matching the Phase 2B-2 `System.getenv()` source-scan lesson - this class's own javadoc explains the legacy classes by name), plus a second, narrower test naming `IacAgentApplication`/`IacAgentController` explicitly. `TerraformAgentController` (a thin, unannotated subclass of `IacAgentController`) was checked and confirmed never instantiated anywhere - dead code, not a bypass.

**Review correctly identified this as necessary but insufficient:** "no live Spring bean reaches `CommandRunner`" is a dependency-graph property, not a capability boundary - the generic `ProcessBuilder`-backed `String... command` surface still physically existed in `src/main` and nothing stopped a future production class from constructing and calling it. Phase 2B-3's actual acceptance invariant is narrower and absolute: `ProcessBuilder` may appear only in `ControlledTerraformProcess`.

**Final remediation (capability removed outright, not merely disconnected):** a dependency check first confirmed nothing in production code legitimately needed the legacy stack beyond itself and `Phase1bTests`: `TerraformCliAdapter` was used only by `TerraformExecutionService`; `TerraformExecutionService` was used only by the now-removed controller wiring; `PipelineRequest`/`PipelineResult` existed only to be `TerraformExecutionService`'s request/response types; `ArtifactSessionManager` existed only to be called by `TerraformExecutionService`. None of `RiskEngine`/`ApprovalEngine`/`ProviderSchemaService`/`PlanJsonParser`/`PlanSummary`/`RiskAssessment`/`DeploymentEligibility`/`RiskLevel` depended on any of the removed classes - those are shared domain types also used by `PullRequestReview`/`ReviewDecisionEngine`/`Phase1bTests`/`Phase1dTests`/`Phase1eTests` and were left untouched. Accordingly: `TerraformCliAdapter.java`, `TerraformExecutionService.java`, `PipelineRequest.java`, `PipelineResult.java`, and `ArtifactSessionManager.java` were **deleted from `src/main`**; `CommandRunner.java`/`CommandResult.java` were **moved to `src/test`** (same package, `com.iacagent.iacagent`) so `Phase1bTests` (`missingTerraformBinaryReturnsBlocked`, `secretRedactionMasksSensitiveValues`, `forbiddenCommandsAreRejected`) keeps exercising the real class directly - it is simply never compiled into the application's production classpath anymore. No production code was left depending on any of them (confirmed by a full recompile of `src/main` with the files removed, which succeeded with no missing-symbol errors), so no "stop and report a dependency" case applied.

**Complete production process-spawn inventory as of this final amendment** (comment-stripped scan across all of `src/main`, every package, not just `runner` or `com.iacagent.iacagent`):
```text
com/iacagent/iacagent/runner/ControlledTerraformProcess.java -> ProcessBuilder (the sole authorized production process-spawning class)
```
No `Runtime.exec`/`Runtime.getRuntime` anywhere in `src/main`. `CommandRunner.java`/`TerraformCliAdapter.java`/`TerraformExecutionService.java` no longer exist under `src/main` at all (verified structurally by `ProductionExecutionSurfaceTests#theLegacyGenericExecutionClassesNoLongerExistUnderSrcMain`).

**New structural regression test - `ProductionExecutionSurfaceTests`** (top-level `com.iacagent.iacagent` package, whole-`src/main` scope, not limited to Spring-annotated classes or any single package): asserts `ProcessBuilder` appears in exactly one production source file (`ControlledTerraformProcess.java`) and that file does reference it; asserts no production source invokes `Runtime.exec`/`Runtime.getRuntime().exec`; asserts no production method declares a parameter list shaped like the deleted `CommandRunner.run(String workingDirectory, String... command)` - a leading `String` parameter followed by a `String...`/`String[]` parameter, the textual signature of a generic "arbitrary executable plus argv" API (deliberately requires the leading `String` parameter so it does not flag unrelated varargs use, e.g. `main(String[] args)` or a helper trying several JSON field-name candidates); and asserts the three legacy class files no longer exist under `src/main`. `LegacyExecutionSurfaceTests` is retained unchanged in scope alongside it - it proves a different, still-useful property (no Spring-wired class references the legacy names by name, protecting against a partial reintroduction even before a full class exists).

## 14. Evidence Model

`TerraformProcessEvidence` is embedded as a new, nullable `RunnerEvidence.terraformProcessEvidence()` field (non-null only for the three Terraform operations) rather than a wholly separate ledger row - `runnerRequestId`/`repository`/`commitSha`/`environment`/`planSha256`/`runnerId` linkage is therefore structural (this record lives inside the `RunnerEvidence` that already carries all of those). Durably persisted as a JSON blob in a new, additive, nullable `runner_requests.terraform_process_evidence` column (`V2__add_terraform_process_evidence.sql` - the V1 schema/columns are completely untouched). Serialization is hand-written (`TerraformProcessEvidenceJson`), not Jackson POJO/record binding, for a fixed and fully-known field set - consistent with this codebase's existing convention of using its Jackson variant only for tree parsing, never data binding.

Deliberately carries no raw stderr bytes ever, and raw stdout only transiently at the `ControlledTerraformProcess`/coordinator layer for JSON parsing - never persisted - per the explicit caution that Terraform/provider tooling output could someday contain sensitive content.

## 15. Process States and Failure Reasons

`TerraformProcessState` (`NOT_STARTED`, `EXECUTABLE_VERIFIED`, `STARTING`, `RUNNING`, `SUCCEEDED`, `COMMAND_REPORTED_DIFFERENCE`, `FAILED`, `TIMED_OUT`, `OUTPUT_LIMIT_EXCEEDED`, `BLOCKED`) is kept deliberately separate from the coarser `RunnerState.TERRAFORM_PROCESS_COMPLETED` (new): `SUCCEEDED` and `COMMAND_REPORTED_DIFFERENCE` (fmt-check found differences - a legitimate, deterministic outcome, never a failure) both map to `TERRAFORM_PROCESS_COMPLETED`; every other value maps to `RunnerState.BLOCKED`. `fmt -check`'s exit-code interpretation is a **documented, deliberate simplification**: exit 0 is treated as "no differences," any nonzero exit as "differences reported" - this phase does not attempt to distinguish "differences" from "a genuine fmt error" by exit code alone, since Terraform's own exit-code contract for this is not stable enough across versions to rely on further without a broader compatibility survey than this phase's scope calls for.

Twelve new deterministic `RunnerReasonCode` values were added (`TERRAFORM_EXECUTABLE_NOT_FOUND`, `_UNTRUSTED`, `_HASH_MISMATCH`, `_NOT_EXECUTABLE`, `TERRAFORM_VERSION_OUTPUT_INVALID`, `TERRAFORM_PROCESS_START_FAILED`, `_TIMEOUT`, `_EXIT_FAILED`, `TERRAFORM_OUTPUT_LIMIT_EXCEEDED`, `_INVALID_JSON`, `TERRAFORM_WORKING_DIRECTORY_UNSAFE`, `TERRAFORM_PLAN_HASH_MISMATCH`, `TERRAFORM_OPERATION_NOT_ALLOWED`); the pre-existing `TERRAFORM_VERSION_MISMATCH` is reused (now serving two related but distinct checks - see its updated javadoc) rather than duplicated. No generic `ERROR` value exists.

## 16. Saved-Plan TOCTOU Handling

`TERRAFORM_SHOW_PLAN_JSON` operates only on the exact staged plan artifact `ControlledRunner`'s own pipeline already hash-verified - never an arbitrary, caller-provided, or repository path (`TerraformCommandFactory.showPlanJsonCommand`'s only path-shaped parameters are internally-derived `Path`s; `RunnerRequest` carries no filesystem-path field at all). Immediately before building the command - not relying on the verification `ControlledRunner` performed possibly seconds earlier - `ControlledTerraformOperationCoordinator.executeShowPlanJson` recomputes the staged file's SHA-256 and compares it against the expected hash; a mismatch blocks with `TERRAFORM_PLAN_HASH_MISMATCH` and the process is never launched at all (`Phase2b3Tests#planHashIsRecomputedImmediatelyBeforeLaunchAndTamperingIsDetected` proves this by tampering with the staged file's content between pipeline verification and coordinator invocation, and asserting a marker the fixture would have created if actually executed is absent). The authoritative bound artifact remains the binary saved plan; its JSON representation is never used to change the recorded plan hash.

## 17. FMT-Check Safety, Including Repository-Source Staging Hardening (amended)

Required arguments (`fmt`, `-check`, `-no-color`, `-recursive`) are always present, and there is no code path that could add `-write` (no such flag string exists anywhere in `TerraformCommandFactory`). Configuration content is staged into the trusted runner workspace via `RunnerWorkspaceManager.stageTerraformConfigFile` (a sibling of `stageArtifact`, not a modification of it - that method's `.tfplan` suffix is specific to plan artifacts) before the command runs, and the staged file is marked read-only by the same mechanism `stageArtifact` already uses. `Phase2b3Tests#fmtCheckNeverModifiesTheStagedConfigurationFile` proves the staged bytes are byte-for-byte unchanged after a real `fmt -check` run.

**Repository-source staging hardening, added on review:** the current `ControlledRunner` `TERRAFORM_FMT_CHECK` pipeline stages exactly one pre-resolved artifact blob via `RunnerArtifactStore` - it involves no filesystem traversal of repository content at all, so it was never exposed to the symlink-escape scenario a real "stage a whole checkout's `.tf` files" operation would face. Since repository content must be treated as untrusted the moment such an operation exists, and a real `fmt -recursive` workflow will eventually need to stage more than one file, the safe primitive was built and fully tested now rather than left for a future phase to get wrong under time pressure: `RunnerWorkspaceManager.stageTerraformConfigDirectory(sourceRoot, workspace, maxIndividualFileBytes, maxAggregateBytes)`. `sourceRoot` itself is trusted (the caller vouches for it as "this request's checkout root"); everything reachable through it is not:

- Every visited filesystem entry - `.tf`-named or not - is rejected outright if it is itself a symlink, checked BEFORE any name/extension filtering. This matters because `Files.walkFileTree` (used without `FOLLOW_LINKS`) does not recurse into a symlinked directory, but critically still delivers it to `visitFile` rather than silently skipping it - checking unconditionally, not only on `.tf`-suffixed entries, is what catches an ancestor-directory escape (`repo/subdir -> /outside`) as well as a direct leaf escape (`repo/evil.tf -> /outside/secret`).
- Every accepted `.tf` file's real path must still resolve under `sourceRoot`'s real path and be a genuine regular file.
- Individual file size and the running aggregate across the whole tree are both bounded (caller-supplied limits) - repository content must not get an unbounded local resource-exhaustion path via `-recursive`.
- The whole attempt is rejected atomically on the first violation - never a partial result mixing trusted staged files with skipped/rejected ones. Accepted files are staged under content-addressed destination names via the existing `stageTerraformConfigFile` - the original repository-relative path/filename is never used as, or to derive, the destination.

New reason codes: `TERRAFORM_CONFIG_SOURCE_UNSAFE` (symlink/escape/non-regular-file), `TERRAFORM_CONFIG_SIZE_LIMIT_EXCEEDED`. Tests: `Phase2b3Tests#leafSymlinkInRepositorySourceIsRejected`, `#ancestorDirectorySymlinkInRepositorySourceIsRejected`, `#ordinaryConfigFilesBeneathTheCheckoutRootAreStagedSafely`, `#oversizedIndividualConfigFileIsRejectedDeterministically`, `#oversizedAggregateConfigSizeIsRejectedDeterministically`.

**Not yet wired into `ControlledRunner`**, stated plainly rather than implied otherwise: introducing an actual "repository checkout root" as a request-scoped input is a request-contract/pipeline change larger than this narrow amendment should make (where does the checkout path come from, how is it tied to the request's identity/commit, who materializes it). The primitive is built, safe, and fully tested, ready for that wiring once a future phase introduces the checkout-root concept - carried forward explicitly in §21.

## 18. Runner Ledger / Approval Integration - No Bypass

All three Terraform operations are dispatched from inside `ControlledRunner.runClaimedPipeline` - after the same durable claim (`RunnerLedgerRepository`), identity resolution, and approval validation every pre-existing operation already goes through; `TERRAFORM_FMT_CHECK`/`TERRAFORM_SHOW_PLAN_JSON` additionally go through the same artifact resolve-and-rehash step `VERIFY_ARTIFACT`/`PREPARE_EXECUTION` use (only the staging call differs by operation). `ControlledTerraformOperationCoordinator` is **package-private**, not public (`Phase2b3Tests#controlledTerraformOperationCoordinatorIsNotPublic`) - there is no way to reach it except through `ControlledRunner.execute(RunnerRequest)`, and no side API such as `showAnyPlan(Path)` exists anywhere. `Phase2b3Tests#duplicateTerraformRequestStillBlocksViaTheExistingReplayProtection` proves a resubmitted Terraform request is blocked by the same `DUPLICATE_RUNNER_REQUEST` mechanism as every other operation, end to end through a real `ControlledRunner`.

A `ControlledRunner` built via the pre-2B-3 8-argument constructor (no `ControlledTerraformOperationCoordinator`) still accepts Terraform-operation requests without throwing - it BLOCKS them with `TERRAFORM_OPERATION_NOT_ALLOWED`, never an NPE, since a runner simply not wired for Terraform capability should fail closed, not crash (`Phase2b3Tests#runnerNotWiredForTerraformBlocksRatherThanThrowing`).
