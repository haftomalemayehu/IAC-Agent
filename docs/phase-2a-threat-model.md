# Phase 2A Threat Model

**Status:** Documentation only. Companion to `docs/phase-2a-execution-contract.md`, which defines the components, checks, and reason codes referenced throughout this document. No executor, runner, or Terraform-execution code exists yet.

**Upstream binding requirements:** `docs/roadmap-phase-2.md` §3 (Required Threat Cases, Security/Trust Boundary) is binding on this document's coverage. `docs/Master-Prompt.txt` §3, §5, and §28 remain in force.

**Method:** every threat is mapped as `threat → trust boundary → attack path → preventive control → detection → expected state → evidence`. Every "expected state" and "evidence" column references the state machine and reason codes defined in the execution contract — this document does not introduce a second vocabulary.

---

## 1. Trust Boundaries

Named once here, referenced by short name in the table below.

| Boundary | What's on the untrusted side | What's on the trusted side |
|---|---|---|
| **LLM/Reasoning** | Model output, tool-call arguments the model proposes, generated Terraform/text, its interpretation of PR/user content | Deterministic control-plane code; the LLM's proposals must pass through that code and can be rejected by it |
| **Repository/VCS** | Commit content, PR description/comments, fork-originated branches | The specific commit SHA and plan hash that were actually reviewed |
| **Approval** | Any claim of approval not produced by the authoritative human-approval workflow (Phase 2C) or, in Phase 2A, its test fixture | A conforming, unmutated approval record (§4 of the execution contract) |
| **Artifact Storage** | The bytes at any given storage location before verification | The bytes whose SHA-256 has just been independently recomputed and matched |
| **Runner/Execution** | Any process not currently holding an authorized, single-tenant execution context for one `requestId` | The specific runner identity checked by `RunnerAuthorizer` for the duration of one execution |
| **Provider/Cloud** | Provider plugin behavior at apply time, cloud API responses | The pinned provider version/checksum recorded in the reviewed lockfile |
| **Evidence/Audit** | Raw process output before redaction | The persisted, redacted evidence record |
| **Control-Plane** | N/A — this is the trusted core itself (executor, validators, state machine) | Same — the boundary here is *internal correctness*, not an external attacker |

**Standing assumption, restated from roadmap §3:** the LLM, all repository content, all Terraform configuration, all PR content, and all natural-language input are untrusted. No value derived from any of them may satisfy an execution precondition, and no code path may let them do so even indirectly.

## 3. TOCTOU Deep-Dive (Threat #22)

Hashing a plan and later applying "the same path" is not, by itself, a guarantee — the path is a mutable reference; the hash was only ever a statement about the bytes observed at one instant. The design must close the gap between that instant and the moment Terraform actually reads the file.

**Attack path in full:** `ArtifactVerifier` reads bytes at T1, computes and matches SHA-256. Time passes (queueing, scheduling, I/O). At T2, `terraform apply` opens what is nominally "the same" path. If anything — a concurrent process, a compromised storage backend, a malicious co-tenant on a shared runner, or even a bug in this system's own staging logic — altered the bytes at that path between T1 and T2, the hash check at T1 provides no guarantee about what actually gets applied at T2.

**A distinction that matters here:** naming a file after its own hash and writing it atomically establishes artifact *identity* (this file's content matches this hash, as of when it was written) — it does not by itself establish *immutability* (nothing prevents a later write to that same path from a process that has write access). The control below treats these as two separate guarantees, layered together, not one.

**Control, as specified in `docs/phase-2a-execution-contract.md` §13:**

1. Verified bytes are copied to a **content-addressed** path (named by their own hash) using atomic write-then-rename, so there is never a partially-written or swappable file at that path — this is the *identity* guarantee.
2. The staging directory's permissions are set so that only the verifying process can write to it, and the content-addressed path is opened read-only by the process that will invoke `terraform apply` — this is the *mutation-resistance* guarantee, and in Phase 2A it is only as strong as ordinary filesystem permissions; it is not a hardware- or kernel-level immutability guarantee, and this document does not claim otherwise. Stronger runtime isolation (dedicated read-only mounts, a runner platform's own immutable-artifact primitives) is deferred to Phase 2B.
3. The hash is **recomputed a second time, as the literal last statement before `exec`**, against the content-addressed path — not "shortly before," but immediately adjacent to process launch, specifically to catch tampering (or bugs) in the residual window.
4. The runner is required to be single-tenant for the duration of one request (the `EXECUTION_CLAIMED` atomic claim, contract §8 and §10, is what actually enforces "no concurrent execution for the same identity" in Phase 2A's minimal-runner scope).

**What this closes:** races between concurrent jobs on a shared filesystem, accidental overwrites, most storage-backend-level tampering windows, and bugs in this system's own file handling.

**What this does not close, and is not claimed to close:** a fully compromised runner host could, in principle, alter its own filesystem or intercept its own `exec()` call between the re-hash and the actual process launch — no userspace re-check can fully eliminate a gap at that level. Closing that residual gap requires either runner attestation, an immutable/versioned external artifact store with its own integrity guarantees (e.g., object-lock storage), or both — both are Phase 2B responsibilities. Phase 2A's contribution is a real, meaningful narrowing of the window, not a claim of eliminating it entirely against a fully compromised host. This is stated explicitly rather than left implicit, per the standing instruction to surface residual risk rather than imply completeness that hasn't been earned.

## 4. Residual Risk (Explicitly Not Fully Closed by Phase 2A)

Stated plainly, cross-referenced to the phase expected to close each gap further, so none of these are silently inherited as if resolved:

| Residual risk | Why Phase 2A doesn't fully close it | Closed further by |
|---|---|---|
| Runner-host compromise after authorization (#13) | No userspace check can fully protect against a compromised host controlling its own execution path | Phase 2B: ephemeral, attested, isolated runners |
| Secret/credential leakage into logs or evidence (#19) | Phase 2A requires redaction but does not yet have a comprehensive, tested redaction pipeline | Phase 2F: secrets/identity hardening with dedicated redaction tests |
| Malicious/misbehaving provider plugin at apply time (#23) | Phase 2A can pin and verify *which* provider runs, but cannot fully constrain *what it does* once running, beyond credential scope | Phase 2B/2F: least-privilege, short-lived credentials; Phase 2D/2E: post-apply verification and drift detection catch the *result* |
| Runner identity strength (contract §14, item 3) | Phase 2A's minimal runner uses a static allowlist, not attestation | Phase 2B: OIDC-based dynamic runner identity |

These residual risks do not block Phase 2A's design acceptance — they are exactly the kind of explicitly-scoped, honestly-labeled limitation the roadmap anticipates a single non-production environment absorbing before the harder problems (real runner isolation, real secrets management) are solved in their own dedicated phases. What would block acceptance is any of these being *silently* assumed solved, which this document is written to prevent.

## 5. Architectural Note: the LLM Must Have No Executor-Reachable Interface

Several rows above (10, 24, 25) resolve to "structural/architectural control" rather than a runtime check. That is a deliberate design position, not a gap: the strongest version of "the LLM cannot invoke execution, and no caller can forge approval" is not a permission check a request has to pass — it is the LLM never having a call path to the executor, and the executor never having a code path that reads approval truth from anywhere but `ApprovalProvider`. Concretely, this means:

- The component that constructs `ExecutionRequest` objects (execution contract §2) must not be a tool exposed to the LLM's tool-calling interface.
- Whatever triggers execution (a workflow step, a scheduled job, a human action recorded through Phase 2C) must be deterministic, not "the LLM decided to call a tool."
- If a future implementation ever needs the LLM to *propose* that an execution should happen, that proposal must be surfaced to a human and go through the exact same Phase 2C approval path as anything else — never a direct or shortcut path to the executor.
- `ApprovalValidator` must never be implemented to accept an optional "inline approval" parameter as a convenience or test shortcut that bypasses `ApprovalProvider.resolve(approvalId)` — even a test-only bypass, if left reachable in production code, recreates exactly the forgery path threat #25 closes.

This note exists so that whoever implements Phase 2A treats "no LLM path to the executor" as an architectural constraint to verify in code review, not an emergent property to hope for.
